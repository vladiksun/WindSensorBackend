## Purpose

Defines backend-configurable post-composition image optimization for the OSM composite endpoint:
an optional, server-side-only stage that quantizes the final composite to a small palette and
emits an indexed PNG, while guaranteeing today's exact behavior when disabled.

## ADDED Requirements

### Requirement: Optimization is controlled exclusively by backend configuration

The optimization mode of composite map images SHALL be determined solely by backend
configuration. The system MUST NOT accept any client/request parameter (query parameter, header,
or body field) that selects, enables, or influences the optimization mode. The existing composite
endpoint's request surface MUST remain unchanged.

#### Scenario: Client cannot influence optimization

- **WHEN** a client requests a composite image with extra query parameters attempting to select an
  optimization mode (e.g. `colors=16`)
- **THEN** the parameters are ignored and the response is produced according to the backend
  configuration alone

#### Scenario: Same request yields mode dictated by configuration

- **WHEN** two clients issue identical composite requests while the backend configuration selects
  a given optimization mode
- **THEN** both responses are produced in that configured mode

### Requirement: Optimization configuration schema and defaults

The system SHALL expose optimization settings under the existing tile-proxy configuration
hierarchy (`osm-tiles.optimization.*`) with exactly two properties:

- `enabled`: boolean, default `false`
- `colors`: one of `original`, `16`, `32`, `64`; default `32`; ignored when `enabled` is `false`

The `colors` value MUST be validated against this closed set. Values outside the set (for example
`15`, `17`, `128`, `256`) MUST be rejected at application startup rather than silently accepted.
The configuration MUST be represented by a typed representation (not raw strings) throughout the
application.

#### Scenario: Defaults preserve current behavior

- **WHEN** the application starts with no `osm-tiles.optimization` configuration present
- **THEN** optimization is disabled and composites are produced exactly as before this change

#### Scenario: Invalid colors value is rejected

- **WHEN** the application starts with `osm-tiles.optimization.colors` set to a value outside
  `{original, 16, 32, 64}`
- **THEN** the application fails to start with a clear configuration error naming the invalid
  value

#### Scenario: Colors value ignored when disabled

- **WHEN** the configuration has `enabled: false` and any valid `colors` value
- **THEN** composites are produced via the unoptimized path regardless of `colors`

### Requirement: Disabled optimization preserves the existing pipeline

When optimization is disabled, the system SHALL produce composite images through the existing
render-and-encode path: full RGB composition followed by standard PNG encoding. No color
quantization, palette conversion, or additional image processing MAY occur on this path. The
viewport calculation, tile placement, opacity, and failed-tile gray fill MUST remain unchanged.

#### Scenario: Disabled mode matches pre-change output

- **WHEN** optimization is disabled and a composite is requested
- **THEN** the response is a 24-bit RGB PNG generated by the existing rendering and encoding path,
  with the same pixel content as before this change

#### Scenario: Failed-tile gray is preserved

- **WHEN** a component tile fails to load while optimization is disabled
- **THEN** the affected region is filled with the existing neutral gray (RGB 192, 192, 192)

### Requirement: Original tiles are never optimized

The upstream tile fetch and tile cache SHALL continue to store and serve original OSM PNG bytes
unchanged. Color quantization MUST happen only once, after all component tiles have been composed
into the full RGB composite; individual component tiles MUST NOT be quantized, and the cached
upstream tile data MUST NOT be modified.

#### Scenario: Tile cache holds original imagery

- **WHEN** optimization is enabled and tiles are fetched and composited
- **THEN** the tile cache continues to hold the original upstream PNG bytes, and reusing those
  cached tiles for a different viewport produces a correctly optimized composite

### Requirement: Real color quantization with a single shared palette

For the `16`, `32`, and `64` modes, the system SHALL reduce the composite to a palette of at most
the configured number of colors using a proper color-quantization algorithm (for example median
cut, octree, or k-means). Simple per-channel truncation or masking is NOT sufficient. One shared
palette MUST be computed over the entire composite viewport so that adjacent component tiles share
identical colors. Quantization MUST be deterministic: the same input image and mode MUST produce
the same palette and the same encoded output.

#### Scenario: Palette size bound

- **WHEN** a composite is produced in a mode with configured color count N ∈ {16, 32, 64}
- **THEN** the resulting image uses a palette containing at most N distinct colors

#### Scenario: Shared palette across tile boundaries

- **WHEN** a flat-colored region spans multiple component tiles within the viewport
- **THEN** that region maps to a single palette entry with no seam or color shift at tile
  boundaries

#### Scenario: Deterministic output

- **WHEN** the same composite image is optimized twice with the same mode
- **THEN** both runs produce identical palettes and identical PNG bytes

### Requirement: Dithering is disabled

Quantization MUST NOT apply dithering (Floyd–Steinberg or any other error diffusion). Flat regions
of the map (land, water, etc.) MUST remain flat after quantization, without introduced
high-frequency noise pixels.

#### Scenario: Flat region stays flat

- **WHEN** a uniform-color region of the composite is quantized to any supported palette size
- **THEN** the region remains a single solid palette color with no speckle or noise

### Requirement: Indexed/paletted PNG output for reduced-color modes

For the `16`, `32`, and `64` modes, the encoded PNG SHALL use indexed (paletted) color type: each
pixel is stored as a palette index referencing the quantized palette, not as a 24-bit RGB triple.
The composite MUST remain fully opaque; no alpha channel MAY be introduced.

#### Scenario: Encoded PNG is paletted

- **WHEN** a composite is produced in a reduced-color mode (16/32/64)
- **THEN** decoding the returned PNG reveals an indexed color image whose palette has at most the
  configured number of entries and no transparency

#### Scenario: Opacity preserved

- **WHEN** a composite is produced in any optimization mode
- **THEN** every pixel is fully opaque

### Requirement: Original-color mode goes through the optimizer

When optimization is enabled with `colors: original`, the system SHALL produce a PNG retaining
the original RGB colors of the composite (no palette reduction), encoded through the same
optimization/encoding stage rather than the legacy path. This mode exists to benchmark the
pipeline independently of color quantization.

#### Scenario: Original mode keeps true colors

- **WHEN** optimization is enabled with `colors: original` and a composite is requested
- **THEN** the returned PNG contains the composite's original RGB colors with no palette
  reduction

### Requirement: Composite cache keys include the optimization mode

Composite cache keys SHALL incorporate the effective optimization mode so that different
representations of the same viewport (different `enabled`/`colors` combinations) never collide.
A cache entry produced under one mode MUST NOT be served for a request resolved under another
mode.

#### Scenario: Mode switch produces fresh entries

- **WHEN** the backend is restarted with a different optimization mode for the same viewport
  request
- **THEN** the previously cached composite (under the old mode) is not served; a new composite is
  rendered and cached under the new mode's key

#### Scenario: Same mode reuses cache

- **WHEN** two identical composite requests arrive under the same optimization mode within the
  validity window
- **THEN** the second is served from the composite cache (X-Cache HIT)

### Requirement: Output PNG is lean and metadata-free

Encoded composites SHALL be optimized for small network payload with reasonable decode
performance on the target device, rather than maximum compression at high CPU cost. The output
PNG MUST NOT carry EXIF or other non-essential metadata.

#### Scenario: No metadata in output

- **WHEN** a composite PNG is produced in any mode
- **THEN** the PNG contains no EXIF or other non-essential metadata chunks
